# LightUp Remediation Source History Studio

**Current posture:** INCUBATE M3/M7 · PLAN/LAB ONLY · DRAFT/HOLD. This is an **offline, local, non-authorizing HUMAN coordination tool**. It never executes remediation, retests, scans, grant creation or network calls. The findings and retest fields are *unverified historic source claims*, not conclusions.

## Complete HUMAN workflow

1. Obtain original exported LightUp five-column CSV snapshots from an **independently authenticated, approved same client + same engagement** private channel. This product does not authenticate clients, operators or files; client/engagement labels and checkboxes are not consent.
2. Enter two local human context labels; confirm you independently verified the same client and engagement. Import up to **12** chronological source snapshots, each ≤ 1 MiB and ≤ 350 findings. The original Casework parser enforces exact columns and canonical source values.
3. Every admitted snapshot is hashed both as exact imported bytes (SHA-256) and as the original **canonical source record digest**. Identical original canonical content is rejected to avoid misleading duplicate timeline points. Use **↑ / ↓** to correct chronological order and change the optional local revision labels without mutating source. The default labels are generic to avoid leaking original filenames in aggregate exports.
4. Review the visual exact original finding-ID history: source severity + source retest status, full remediation text in per-finding timeline, changes/appearances/disappearances, severity changes and retest label changes. Missing from a later source is **NEVER evidence of remediation**, and `fixed` is **only the original unverified source label**.
5. Choose any two chronological source revisions for an **exact original-source pair diff**. Original unchanged `LightUpCasework.compareSource` computes appeared, absent, exact-changed and unchanged original finding identities; the Pair Desk also shows original severity changes and retest-label changes. Pair aggregation exports only counts/hashes, while separately confirmed PRIVATE original-ID pair export includes original titles and remediation suggestions. A source change is a human question, **not** independent proof of a fix. Filter the full timeline by original IDs, titles, human owner, critical/high labels or source-change category. Attach tentative local HUMAN owner, next discussion/action and due date. These annotations live in memory and never modify any original finding.
6. Export aggregate CSV source trajectory counts (no original IDs, titles, remediation text or HUMAN notes); or explicitly acknowledge a separate approved PRIVATE recipient/destination and export the currently filtered original-ID HUMAN handoff CSV. CSV formula-like fields are spreadsheet-escaped. Downloads remain private on the operator device and are **not** deleted by the application.
7. For a **source-exact encrypted local save/resume**, tick the private destination acknowledgement, enter a unique passphrase of 14–256 characters, and select **Save encrypted PRIVATE checkpoint**. AES-256-GCM uses Web Crypto, PBKDF2-SHA256 with 600,000 iterations, random 16-byte salt, a unique 12-byte IV and authenticated application-context binding. The encrypted checkpoint stores the original exact CSV bytes, both SHA-256 identities, revision labels and HUMAN notes. Restore requires Forget/empty workspace plus independent re-confirmation of the same exact client and engagement; the application authenticates the local AES-GCM envelope, reconstructs every original source via unchanged `LightUpCasework.parseCSV`, rechecks file-byte **and** canonical-source SHA-256, rejects duplicates/unknown notes and changes in-memory state atomically. The checkpoint does not authenticate the creator/client or confer consent. **Keep the passphrase and encrypted export private; forgotten passwords cannot be recovered.**
8. Click **Forget** to clear imported original records and HUMAN notes from the live app memory. No `localStorage`, cookies, IndexedDB, network, external scripts, telemetry or file uploads.

## New original-row-bound HUMAN continuity (19 October 2026)
- HUMAN notes are **bound to the exact original five-field finding record**, not merely the reusable finding ID. If the current newest imported source modifies title, severity, retest label, remediation or identifier, the existing note becomes **HOLD**, is not included in a current-source HUMAN handoff and cannot be silently edited/reassigned. Notes for missing latest-source findings remain HOLD; absence is never evidence of remediation.
- The **HUMAN notes on HOLD** filter shows previously created notes that need a decision. Select a row to inspect the prior original note-bound fields against the current original five fields. An explicit checkbox and separate human confirmation are required to carry only the HUMAN owner, action and tentative date to a new exact original source record. No source claim, grant, real remediation, retest or authority changes.
- A PRIVATE original-ID timeline CSV includes a `human_source_binding` field: `EXACT_ORIGINAL_ROW`, `HOLD_STALE_OR_MISSING`, or `NO_NOTE`. Held notes are *never* included as live note text in that handoff, and the counter shows skipped notes.
- **Export original Casework v1 PRIVATE human draft** integrates directly with the **unchanged native original `LightUpCasework.makePacket`**: it builds a complete five-column-source-bound native packet from the latest original CSV. Only exact-row-bound human owner/action/date fields populate original Casework; absent, changed or unbound HUMAN notes are omitted, and the output only labels work as HUMAN `planned` / `unassigned`. The original false-only authorization, consent, grant, scan, verified-retest and release fields are preserved.
- An existing encrypted checkpoint created before original-row binding may still be loaded under the same strict encrypted/original-source agreement, but its legacy unbound notes remain HOLD until separately reviewed by an operator. New checkpoints include and validate every referenced original five-field note source against the original SHA256-verified snapshot list.
- Concurrent original CSV import and source mutation fail closed before committing data. Pending encryption observes local HUMAN note changes via revision sequencing. CSV spreadsheet exports also protect against leading hidden Unicode format/bidi characters and compatibility (NFKC) formula prefixes without rewriting original source values.

## Native PRIVATE Casework v1 round-trip (same exact original source)
1. Import original five-column findings CSV snapshot(s), with the latest snapshot corresponding exactly to the original Casework source. Confirm the same separately authenticated private client/engagement locally.
2. Select the **original Casework v1 PRIVATE JSON** (up to 2 MiB), optionally review and separately preserve any current notes, then explicitly approve replacement. The importer parses JSON with duplicate-key rejection at every nesting level, calls the **unchanged native `LightUpCasework.loadPacket`**, requires complete exact five-field matching finding identities **and identical original SHA-256**, and enforces all twelve non-authority flags **false**. Any mismatch leaves the current HUMAN workspace intact.
3. Original HUMAN owner/next action/tentative due date and the complete original Casework status, blockers, verification-plan notes, free-form notes and human update timestamp are preserved as **unverified HUMAN claims** bound to exact source rows. They can be reviewed in each finding detail and saved to the existing encrypted PRIVATE workspace.
4. Native Casework export preserves those original HUMAN-only Casework fields if exact original source-bound; it applies updated private HUMAN owner/next action/due values only for that exact row. For a new local note it uses `planned` or `unassigned`, never a claim of verified remediation. If source fields change and a HUMAN note is explicitly carried after original field comparison, any previous Casework status/lineage is deliberately **cleared**: the old HUMAN claim is not transferred into the new original finding.
5. Existing notes are never silently replaced by native Casework import. HUMAN HOLD notes remain inside encrypted backups, not in stale new-source handoffs. All security-relevant flags remain false, with no scan, authentication, consent or grant execution.
