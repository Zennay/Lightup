# Offline scope-review: synthetic manifest inode consistency — #1418

**Project status: INCUBATE M3/M7 · PLAN/LAB ONLY.** This is a Python-only, opt-in test/proof; never authority to issue a customer grant, run an assessment or deploy.

## Defect class covered
The existing developer-only `sitecustomize` fixture validates a manifest pathname before it invokes its guarded `os.open` and enrolls the resulting integer FD for reads. Path identity alone does not prove the returned descriptor refers to the same originally admitted local file if a path or lower-level open operation is swapped after admission. A symlink into an allowed path can also create misleading path aliases.

## Implemented test boundary
The new independent test `tests/test_scope_offline_cli_manifest_inode_20261014.py` *extends* the existing no-network/no-write/non-authorizing hook, without touching the source-owner runtime. At child startup, it records the exact `st_dev` and `st_ino` of the three synthetic, regular local manifest files that actually exist. On `os.open`, only exact canonical built-in str or concrete `Path` names among those three manifests are accepted; relative traversal and symlink aliases fail hard. After the existing protected `os.open` returns, `os.fstat(fd)` must match the startup-pinned identity and regular-file type **before** the wrapper returns the FD. Failures cause uncatchable exit 92 rather than accepting a stale descriptor.

A disposable negative control opens a symlink alias to a synthetic manifest. A second intentionally replaces the low-level test hook's returned descriptor with one pointing at an entirely fictional decoy file, simulating the dangerous gap between prior path admission and opened-object identity; no file contents are read. Both run under swallowed `BaseException` but require exit 92, zero stdout/stderr and byte-identical fixture files. A positive control opens and reads a **synthetic approved** descriptor, then closes it. Actual source registry-review equal and drift/HOLD cases plus the opt-in finite NUMBER reviewer valid/HOLD cases still execute with all five authority/permit/execution/merge/release flags `false`.

## Explicit limits and release gates
An inode check is *not* a complete content-integrity seal (an existing inode may be edited), tamperproof filesystem root, OS sandbox or protection against arbitrary native syscalls and pre-bound references. A child with unrestricted Python may mutate test hooks; these are detector regressions, not confinement claims. All negative files and paths are fictional and disposable. No real customer assets, host-private reads, networking, active scans, grant issuance, production source, shared runner/workflow or deployment changes. Exact immutable-head hosted Python3.11/3.14 units and genuine producer integration jobs are required before a source-only merge; a registered permanent VPS runner and independent human security/privacy release remain separate prerequisites for live authorization.
