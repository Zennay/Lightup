# Scope Readiness Workspace — private local human coordination (DRAFT/HOLD)

Open `coordination/scope-readiness.html` locally from this PR checkout. This is a **user-facing, static coordination product**: no installation, network, account, database, service, targets, DNS, API calls or browser persistence. It is deliberately separate from the actively owned authorization domain/source and the separate Studio, client CLI and operator desk branches.

## What it delivers

1. Import one or several **real LightUp Scope Planning Studio v1** `lightup.scope_proposal_draft` JSON files produced by [Scope Proposal Studio PR #1567](https://github.com/Zennay/Lightup/pull/1567). Each source is bounded to 64 KiB; up to 20 different versions per board. Reject non-`DRAFT_ONLY` or explicitly positive authority/consent/grant fields. The imported asset values, client free-text notes and source files never enter exports. Each record receives SHA-256 of **its exact original UTF-8 source bytes** (not the Studio's stable fingerprint).
2. Plan six concrete preparation tracks **per distinct draft version**: client identity/asset ownership evidence, exact scope/exclusions, client consent coordination, independent operator review, risk/window/revocation & STOP coordination, and evidence privacy/incident handoff. Each track has an optional coordinator label, target date, next action/blocker and one of *not started*, *waiting* or *prepared but unverified*. **A prepared checklist is not a signature or validated permission.**
3. Track aggregate outstanding preparation work, overdue target dates, the number of sources that must be re-attached, and a **separate-coordinator-label overlap hint** when the client-consent and operator-review tracks carry the same self-reported name. Filter for incomplete, source-missing, risk-4, overdue or overlapping-coordinator cases; sort by attention priority, draft title or earliest outstanding action date. An overlap flags possible missing separation for **human** follow-up: aliases are unverified and a different label never proves real independent approval. Operator-friendly details and a printable review brief identify specific blockers.
4. Download a **private local, review-only workspace JSON** containing source SHA hints, limited proposal metadata and user-entered coordination actions, without target identities, raw asset names, full Studio payloads or notes. Restoration is atomic, revalidates strict version/security/state structure, and **marks every source as unbound** until the same original file is reselected and SHA-256 matched. Older notes cannot silently acquire new source meaning.
5. Export a private, formula-safe CSV action register suitable for coordination spreadsheets. Every row expressly says authorization **NO**. Only user clicks download files; no auto-save to browser storage, telemetry or remote upload.
6. **Revision-safe follow-up reuse:** select a second draft and deliberately copy only human coordinator labels, suggested deadlines and next-action text to an otherwise untouched draft. Reject nonempty destinations, ask explicit confirmation, surface differing client labels/risk/mode/asset counts, and reset every imported task state to **not started**. Prepared paperwork and anything resembling client/operator approval never transfer across revisions. Matching counts are not proof of identical effective scope.
7. Unsaved-change confirmation, full local reset, source file batch atomicity, bounded tracking input and accessible mobile-friendly layout.

## Native client intake vs full-fidelity private handoff — structural preview

The new **Studio → authenticated client request** routing panel inspects one reattached original Studio v1 draft and applies the *documented lossless representation constraints* from the independent client-intake source owner [PR #1571](https://github.com/Zennay/Lightup/pull/1571) read-only. It highlights the cases where a normal native request would drop material safety constraints:

- **Explicit exclusions:** the persistent request cannot enforce excluded assets; dropping them could silently widen scope.
- **`analysis_only` mode:** the native CLI intentionally refuses automatic conversion into an authorized-assessment request.
- **Private-lab network checks:** the dedicated lab workflow is required.
- **Any proposed local window / incompatible UTC provenance:** the durable native request lacks equivalent schedule enforcement. Use the full operator handoff, not an unconstrained request.
- **Requested risk 4:** explicitly prompts separate human risk escalation review, even when other proposal fields are structurally compatible.

Hard representability blockers yield `PRIVATE_HANDOFF_REQUIRED` and **HOLD for native submission**. No blockers yields only `NATIVE_PREVIEW_POSSIBLE_NOT_AUTHORIZED`: this **does not** imply the draft passes the authenticated client CLI, `DomainStore`, operator review, consent, independent risk approval, revocation or scope policy. The panel never rewrites the original Studio JSON to remove exclusions, never creates a request and never edits another source owner's PR.

An optional privacy-minimal `lightup.scope_native_intake_route` JSON download records only original unsigned source SHA-256, blocker categories, human-routing designation and hard-false security flags. It omits target assets, client labels and free-text notes. Replacing/restoring/clearing original files invalidates the local classification. The full-fidelity handoff feature itself remains owned by #1571 and is explicitly separate from this offline review interface. Its branch has not been merged/released.

## New: source-bound Studio revision impact workflow

A new **Scope revision impact** panel compares two distinct, fully reattached original Studio v1 JSON exports **inside browser memory**. The tool stores source objects only in a volatile in-tab `Map` keyed by SHA-256 of exact original file bytes. Source payloads do not enter the saved casework schema, printed overview, CSV, iCalendar or private change summaries. Restoring a saved workspace clears volatile source copies; reattach exact originals before reviewing. Removing a draft or clearing the board discards corresponding source objects. A changed file/import invalidates the comparison before actions can run.

The privacy-minimal reviewer identifies proposed request/exclusion **literal label** additions/removals, requested risk/mode, proposed activities, UTC/local windows and timezone provenance, notes, client labels and proposal titles. It maps those categories to the six human preparation workstreams and creates a private **`REVIEW_ONLY`** JSON impact summary containing only anonymous source hashes, change categories and affected workstream IDs, with every authority/grant/consent/release flag false. It cannot infer actual CIDR membership, DNS resolution, current client ownership, authenticated tenancy, operator approval or revocation status. A changed host or subnet declaration is **not** treated as proof of either safe narrowing or approved expansion.

The operator can explicitly **reopen** impacted preparation workstreams on the *updated draft only*, moving previously prepared/blocked paperwork states to `todo` while keeping user-entered owner/deadline/follow-up notes. The impact preview now lists a separate, concrete human next step for each affected workstream (e.g. new ownership evidence, exact scope validation, independent review, STOP and revocation). When reopening, these suggestions fill **only empty** action fields; no existing text is overwritten and the user is warned to revisit potentially stale notes. The original draft remains unchanged. The local action never contacts a target or issues/withdraws grants. The preview is exact-source and edit-epoch bound: any intervening edit, imported source, restore, selector change or source removal forces a fresh comparison before action.

Separately, **Copy missing follow-up logistics** fills only empty owner, due date and next-action fields on an unfinished updated draft from the chosen baseline. The self-reported client label must be identical (a mismatch is a hard HOLD, while a match still **does not prove tenancy**). Earlier action instructions are specifically **not copied into changed workstreams** where they could become stale. No status, prepared evidence, consent, authorization, risk approval or source data transfers, and nothing is overwritten. A new comparison is required after applying the copied fields. Both actions require explicit human confirmation.

## Conflict-free offline teamwork

The **Merge separate workspace** input accepts a second strictly bounded private `lightup.scope_readiness_workspace` v1 JSON snapshot. The import preview checks each source SHA-256 identity and normalizes the full source metadata and six paperwork task records. Identical snapshots of one source are counted once; genuinely new source records can be added as **UNBOUND** up to the 20-source cap, but any differing task/metadata content for the same source digest triggers an explicit **HOLD** with only a digest-prefix identifier. There is never a "last write wins", forced overwrite, promotion of old source-bound metadata, transfer of consent, or assumption that two offline copies are authoritative. When the same source SHA-256 appears with conflicting contents, the UI now names the **affected proposal metadata fields and human-preparation workstreams**, without disclosing either version's original private values. This points humans to the exact documents they must reconcile; conflicts still abort the entire merge.

The preview does not change the current workspace. If it is conflict-free, applying it requires a separate confirmation and rechecks source collisions and bounds atomically before adding records. Any intervening manual edit, imported original source or restored workspace invalidates the pending preview. Existing notes, assignments, task statuses and source-attachment state are retained. New draft sources must be separately re-attached by exact original-file digest. Merge remains a private human coordination feature; it does **not** resolve or combine authenticated client/operator approvals and may not be used as a release gate.

## Six-lane preparation action board

The workspace now shows an actionable, read-only **human follow-up board**, grouped by the six preparation stages across up to 20 drafts (maximum 120 preparation items). Select incomplete, overdue, unassigned or waiting/blocked work. Each lane surfaces nearest target dates first with visible HOLD markings for unbound original sources, and displays up to eight immediate action links with remaining-work counts. Selecting an action opens the exact draft and scrolls to the matching edit row. Changing client/operator coordinator labels refreshes the live human-independence warning and prioritized queue without deleting or rewriting in-progress form input. The board never infers authenticated user identity, client asset ownership, risk approval or scan permission.

## New: multi-draft action planning and separate recipient packets

The **Batch follow-up planner** supports a selected workstream across the current filtered review queue, all source-attached drafts or every local draft. Enter a coordinator label, paperwork target date and/or next-action template; preview all eligible assignments first. Preview reports number of touched records and unbound-source HOLDs. Applying requires explicit confirmation, fills **only empty fields of incomplete tasks**, and never overwrites existing values, marks a task `prepared`, carries approval state forward, or grants access. A change to underlying data or batch selection invalidates the preview. Prepared records and human-decided task statuses remain untouched. The most recent applied batch is reversible with **Undo last applied batch**: the browser preserves only the exact pre- and post-assignment values, verifies all records still match the applied state, and restores the original values after confirmation. Any subsequent edit or file restore invalidates Undo rather than risking accidental overwrites. Undo itself is a local coordination edit, not authorization.

The **Separated preparation briefs** workflow produces two distinct, private local Markdown packets:
- **Client-side:** only ownership-evidence and client-coordination preparation tasks; omits internal operator checklist items.
- **Operator-side:** only scope/exclusion, independent operator, UTC/risk/STOP and privacy/incident-preparation tasks; omits client-coordination notes.

Both can address a single selected draft, the filtered draft queue or the entire workspace. They include precise unsigned source digest hints, explicit UNBOUND-source HOLDs, strictly non-authorizing activity descriptions and dates, and **literal FALSE** statements for authenticated consent, approval, grant, current revocation, execution, scan and release. They omit original proposed target asset values, excluded-asset details, source free-text notes, client labels and assigned coordinator names. User-entered next-action text is still potentially sensitive; inspect the preview and manually verify the intended recipient. No messages are sent and nothing is uploaded. Any subsequent source/assignment change invalidates the preview; download demands separate confirmation.

### Private paperwork calendar handoff

The **VTODO deadline export** creates a local RFC 5545-style `.ics` calendar task list for the selected draft, filtered review queue or all draft records. It includes only unfinished paperwork tasks with an explicitly assigned target date (max 120 tasks), a random per-export UID, static anonymous task category and draft ordinal, due date and explicit `X-LIGHTUP-AUTHORIZATION:FALSE` and `X-LIGHTUP-CONSENT:FALSE`. It never creates `VEVENT` assessment slots or bookings and omits client/project names, assets, digests, coordinator names, action notes, contacts, consent claims, risk decision or grants. All events are `VTODO`, `CLASS:PRIVATE`, `STATUS:NEEDS-ACTION` and marked preparation-only. Because many calendar providers sync imported `.ics` tasks, the operator must choose an approved destination deliberately; **the local tool does not connect to a calendar or upload anything**. Any source-unbound deadlines are counted and explicitly warned about before manual export.

Neither a stage marked `prepared` nor a local client/operator packet equals authenticated consent or operator approval. Source continuity hashes do not prove that two different clients or people consented. Separation of packet content protects against casual over-sharing but cannot authenticate a recipient.

## Readiness is not authorization

This is a paperwork tracking board, not an approval queue. Even if every row says **prepared**, the board remains **REVIEW_ONLY / DRAFT-HOLD**, all exported `authenticated`, `client_consent`, `operator_consent`, `authorization`, `risk_approved`, `grant`, `revocation_checked`, `execution`, `scan`, and `release` security flags are **literal false**. Imported source labels, source SHA-256, due dates, coordinator names, prepared fields, selected risk levels and printouts are **self-reported** and do not establish authenticated identity, possession of an asset, client consent, operator approval, approval of a proposed risk-4 activity, action-time scope/revocation enforcement or permission to contact a target.

Source validation is about **local format and source continuity**, not domain validation. A standalone HTML file must never be allowed to create `DomainStore` records, grants, operator approvals or scan/execution requests. For real workflows use the separately authenticated request/approval routes after the original release gates; independently verify client asset ownership and action-time revocation.

For privacy, exported snapshots still contain human-entered owner labels, action notes, calendar targets, source fingerprints and possible project labels. Store/share them as potentially sensitive internal casework; avoid pasting personal data, credentials, asset hostnames or client secrets into action notes. The source asset contents are never sent to the board export. An exported JSON or CSV is unsigned and editable.

## Example workflow

Create `lightup-scope-draft.json` in the Studio. Open the local `coordination/scope-readiness.html`; select one or more Studio drafts. Assign a coordinator label and action date to each missing workstream. Mark a task **prepared but unverified** when the preparatory artifact is gathered; keep real sign-offs in the authenticated systems. Export the private register before closing the tab. When resuming, import that register and re-attach the exact Studio JSON files; unbound sources remain prominently HOLD. Export a CSV and send it only through separately approved internal channels.

The import also verifies source-local planning-wall-time versus UTC offset fields when a Studio source claims a resolved UTC window; contradictory dates or ambiguous/unsupported time-status metadata are refused. This remains a consistency check, not an approved booking.\n\nRestored private workspaces strictly refuse unknown top-level or authority-like fields, unknown or positive security flags, prototype-related reserved JSON keys, malformed UTF-8 and explicitly attached-source claims. Local snapshots are never accepted as authenticated authority.\n\nThe v1 snapshot schema is `kind: lightup.scope_readiness_workspace`, `schema_version: 1`, `disposition: REVIEW_ONLY`, mandatory false `security` flags, and an array of strict per-source action registers. Snapshot maximum 256 KiB; source maximum 64 KiB; no silent partial batch import.
