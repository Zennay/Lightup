# Offline review change narrowing — W9

**LightUp INCUBATE M3/M7 · PLAN/LAB ONLY · DRAFT/HOLD · NO MERGE · NO DEPLOY.**

This separately opt-in, local-only helper answers a limited question: *does a proposed batch of review-metadata requests differ from an earlier batch only by narrowing existing request labels, windows, capabilities or risk?* A passing result means **shape-only narrowing**, NEVER that either input was a genuine permission, approved authorization, executed assessment or trusted customer record. It never contacts targets, connects to services, imports an active executor or persists anything.

## Use

```sh
python scripts/check_scope_review_delta_offline.py /private/previous.json /private/proposed.json
python scripts/check_scope_review_delta_offline.py --require-private-file /private/previous.json /private/proposed.json
python -m unittest discover -s tests -p 'test_scope_review_delta_offline.py' -v
```

Each input must independently satisfy the existing single/batch shape contract (1–32 sorted complete canonical JSON records per file, ≤64 KiB each, local regular-file checks). When `--require-private-file` is selected, **both** inputs must pass existing POSIX owner-only, single-hardlink and parent-path privacy checks. A missing or unsafe file produces a fixed-code HOLD without echoing paths.

## Conservative non-widening checks

Identity binding uses exact `request_id` as the key; a proposed row absent from the earlier snapshot is held as `ADDED_REQUEST`. Every retained request must preserve **exact tenant, asset and requester labels**, **original purported authorization/scope references and evidence digest list**, and **exact mode**. The helper does **not** assume mode names form a privilege hierarchy: even switching from target-active to lab-active is a review HOLD. Risk must not increase; proposed capability labels must be a subset of existing labels; the proposed UTC time window must be contained within the previous review window. Removals of existing request rows are allowed as narrowing, but an entirely empty proposed batch is deliberately refused by the underlying version-1 schema. Inputs and changes are checked in memory and never rewritten.

Any widening, malformed packet, ambiguous/duplicate request ID, altered provenance or incomplete batch returns `HOLD` and three **zero counts**. A passing result is `REVIEW_ONLY` with only aggregate counts for `retained_requests`, `removed_requests`, `narrowed_requests`, plus a fixed status/reason and `non_authorizing=true`. All five flags stay strictly `false`: `authorization_verified`, `permit_issued`, `execution_enabled`, `merge_approved`, `release_approved`. Receipts contain no tenant/asset/request IDs, evidence digests, paths or other input values. Exit status is 0 for non-authorizing review-only, 2 for HOLD.

## Threat model and explicit exclusions

- Both snapshots are **untrusted inputs**. This tool cannot prove that the earlier snapshot was authorized, current, immutable, authentic or even generated by LightUp. A fake earlier snapshot can make the proposed snapshot appear syntactically narrowed. It must NEVER feed a permit or executor dispatch gate.
- There is no authenticated owner, digital signature, chain of custody, capability lease, revocation lookup, current clock/grant check, durable transaction, cross-run replay protection, real-target scanning or authorization.
- A changed mode or provenance requires independent re-review; this offline CLI does not offer a way to approve change or elevate risk. The comparison's lexical UTC ordering relies on the canonical date/time admission performed **before** any comparisons.
- Real source-owners must enforce authenticated live grants/tenant asset lineage, exact scope and risk, STOP control and other production invariants at every dispatch, separately from this diagnostic. Hosted and independent permanently registered VPS CI on the exact latest commit, security/privacy/source-owner review, latest-main compatibility and explicit human release are still required.

The accompanying 23 synthetic tests exercise permitted removal/narrowing, all denial classes, malformed inputs, duplicate-key parse rejection, batch atomicity, CLI behavior and false-only receipts. There are no customer systems or targets in test fixtures.

## W11 stronger private-path integrity — descriptor-relative POSIX open

In the optional `--require-private-file` mode, the local file reader now opens parent directory components **relative to already opened directory descriptors** using `O_DIRECTORY | O_NOFOLLOW`, then opens the final regular-file component using `O_NOFOLLOW` and the parent directory descriptor. These checks run in addition to the earlier privacy/owner/hardlink/metadata checks. If a directory is replaced with a symlink **after the initial lstat but before opening**, descriptor-relative no-follow semantics fail with an opaque `INPUT_UNAVAILABLE` HOLD. If the platform lacks descriptor-relative `os.open` or POSIX no-follow capabilities, requesting the stronger private-file mode yields fixed-code `PRIVATE_PATH_UNSUPPORTED` HOLD rather than silently falling back to a weaker check. The default non-private read path retains its original behavior for purely synthetic fixtures.

The new synthetic POSIX regression suite `tests/test_scope_review_dirfd_offline.py` tests real renamed-parent and swapped-final-file race simulations, symlink checks even if the preliminary check is artificially bypassed, old public-file compatibility, unsupported-platform denial, expected descriptor flags, path-safe CLI errors and closure of directory file descriptors. No real target is contacted. Even a successfully read file **does not authenticate its content or confer any grant**. This protects only local path traversal against certain symlink substitutions; it is not a trusted file-origin attestation, complete fix for all namespace/mount races or a substitute for source-owner security review and explicit human release.
