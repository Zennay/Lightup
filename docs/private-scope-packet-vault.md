# Private Scope Packet Vault — offline encrypted handoff (DRAFT/HOLD)

**Status:** LightUp INCUBATE M3/M7 · PLAN/LAB ONLY · DRAFT/HOLD. This is human-preparation tooling, **not** client identity, signed evidence, verified approval, authorization, a scanner, a permit, or release readiness.

## Use it

For the easiest use, download and open the [single-file standalone vault](../scope-vault/standalone.html), reproducibly produced by [the builder](../scope-vault/build_standalone.py) with exact inline CSP hashes. Alternatively, open [scope-vault/index.html](../scope-vault/index.html) in a modern browser that supports secure-context Web Crypto. The page has **no dependencies, backend, network requests or persistent browser storage**. Save the three files `index.html`, `style.css` and `vault.js` side by side, then open `index.html`. A browser that denies Web Crypto to file URLs will refuse encryption; use a browser that permits Web Crypto in a local secure context. Do not host on a public site or disable CSP to work around it.

1. Choose one or more *non-secret*, UTF-8 draft files (.json, .md, .txt, .ics or .csv; up to 12 files, 512 KiB each, 2 MiB total). Studio v1 proposals, private coordination drafts and anonymous schedule handoffs can be preserved **as opaque files**. The vault never validates their authorization semantics and never replaces the canonical source-side validation.
   Use the per-file **self-labelled review role** selector to distinguish unverified client proposals, operator notes, scope revisions and schedule handoffs. Roles are kept inside the ciphertext and do not authenticate anyone. Older same-format packets without roles restore as Unclassified.
2. Enter the same passphrase of at least 14 characters twice. Click **Download encrypted** to obtain `lightup-private-scope-packet.lightup-vault.json`. Store the passphrase separately. There is no backend and no recovery service.
3. To restore, choose the saved encrypted JSON and enter the passphrase. The entire payload must pass authenticated decryption, exact schema checks, digest verification, UTF-8 validation, filename and byte limits **before** any prior in-memory workspace is replaced.
4. Original decrypted files are downloaded only by an explicit secondary click and confirmation. Anyone with access to that plaintext download can see the contents. Click **Lock immediately** to clear retained in-tab buffers. Hiding the tab automatically locks unless an operation is in progress; inactivity also locks after five minutes. The browser and OS may retain transient copies outside JavaScript's control.

## New multi-document review and recipient handoff workflow

- **Selective encryption:** Each file in the local inventory has an Include-in-handoff checkbox. Use Select all/Select none and deliberately choose the subset to encrypt. The rest remain in memory but do not appear in the ciphertext being saved. You must explicitly confirm a visible local list of filenames and self-reported roles before downloading.
- **Recipient-specific route:** Before sealing choose `private-archive`, `operator-review` or `client-review`. A client-review packet **refuses** unclassified or operator-note-labelled items; only client-proposal, revision and schedule roles are accepted. This is an **accidental disclosure guard**, not destination authentication, client permission or a safe replacement for a human checking the address and intended recipient. The route lives inside the encrypted payload, not the public envelope; legacy vaults without a route load as private archive.
- **Atomic multi-vault merge:** When unlocking a second vault, opt in to Merge. Matching filename + digest + byte count + role + internal memo/stage is deduplicated, while conflicting names/roles, file caps and oversize collections cause an atomic refusal without changing the previously loaded collection. The sender's role labels and filenames remain **unverified assertions**.
- **Local revision reading:** Select an original and a changed UTF-8 file, then preview source text or inspect additions and deletions using a bounded line-diff. Input is rendered exclusively via `textContent` and never interpreted as markup or executed. Each file is limited to 400 lines of at most 2,048 UTF-16 characters for visual comparison. Diff counts are a convenience **text** signal, not semantic scope-membership evaluation, consent, verified principal identity, grant validity or safe execution authority.
- **Confidentiality:** Text view and diff are visible on your own screen while open; Hide, Lock, tab hiding or workspace change removes this UI output. Browser-managed strings may remain in inaccessible memory. Downloading a plaintext file is explicitly manual and cannot be undone.

All actions remain offline. To get the newest self-contained UI, download the freshly built `scope-vault/standalone.html`; source files `index.html`, `style.css` and `vault.js` are the inputs to its reproducible build.

## Encrypted private casework and re-encryption

Each imported draft has a **local human-preparation stage** (unsorted, needs clarification, in progress, prepared for human review, superseded) and an optional plain-text **internal reviewer memo** of at most 600 UTF-16 characters. These stages never mean client/operator approval, grant issuance, valid scope or permit. The document inventory can be filtered by stage; filtering does not change encrypted source bytes or scope identity.

Internal review memos and preparation stages are stored **only in encrypted private-archive and operator-review packets**. A `client-review` export explicitly omits both fields, even if the file's self-reported role says client proposal. Human reviewers must check the **original file contents** independently before sharing; the app cannot redact credentials embedded in the source itself. A best-effort local credentials heuristic blocks some common bearer-token, private-key, credential, and cookie patterns in client exports. This does **not** prove content is free of secrets and can reject harmless examples. Do not change the routing label to evade a hold; remove/redact the problematic content in the source and re-import it. Client-facing packages also require every selected file to carry the private `Prepared for human review` stage, not merely to avoid the historical stage. Unsorted, clarify, drafting and superseded drafts are held. That manually assigned stage is a PREPARATION label, not consent, scope authorization or a human release decision.

Use **Suggest recipient-safe selection** to preselect files by their self-labelled role and local stage, followed by an explicit human confirmation. The default All/None buttons still operate on the entire inventory, even when a stage filter is selected.

**Recommended confidentiality default:** after a successful encrypted export, the workspace automatically locks, clears retained file buffers, hides comparison output and empties password fields. Uncheck the clearly labelled setting only if you need to keep working on the unlocked drafts. For a **client-review, operator-review or partial archive**, automatic locking discards all other unsaved internal notes/stages. The app therefore requires a separate explicit DATA LOSS confirmation before proceeding. Prefer sealing an entire private backup first. This cannot securely erase browser/OS copies, downloaded plaintext files or ciphertext already shared.\n\nTo rotate an archive's passphrase: locally unlock your previous encrypted file, supply a new strong passphrase and confirmation in the seal form, and choose **Re-encrypt entire private archive**. This intentionally seals *all* in-memory documents and internal notes, even those currently unchecked for recipient sharing; it always chooses private archive and creates a fresh random salt/IV. The output has a different local filename. Existing packets remain decryptable with their previous passphrases; the app cannot revoke old downloads or files already sent to others. Delete or retire those separately according to your retention policy.

Backward compatibility: previously exported packets with no internal stages or notes recover with `unsorted` and an empty note. Full merge refuses conflicting **explicitly supplied** memo/stage values as well as conflicting same-name bytes or self-reported roles. A client packet deliberately omits private metadata: if its bytes, name and role match an already-open local document, merging preserves the existing private note/stage rather than interpreting absent values as a conflict. Missing private metadata never erases an existing review memo. This prevents silently losing private human preparation history. Client packets cannot contain these internal fields.

## Source-bound local privacy editor (recipient handoff preparation)

The local **Create a privacy-edited review copy** workflow is intended for draft documents that contain obvious confidential strings and cannot yet be shared. It never contacts a remote target, secret-management service, provider or scanner. It is not consent or a grant.

1. Choose a local UTF-8 source file and optionally enter one exact sensitive literal of 6–128 characters to remove. The optional value is held only in the form during processing and cleared immediately on invocation; browsers can still retain transient string copies. Enable/disable common-pattern masking independently.
2. The editor substitutes a limited set of recognized private-key PEM blocks, bearer authorization headers, named credentials, AWS-style access-key IDs and cookies. It can also replace occurrences of the exact literal specified in the form. It refuses a no-change operation, oversized edited output, duplicate-derived filename, exhausted inventory capacity or any remaining **recognized** sensitive pattern. Errors never contain matched secret bytes.
3. An explicit human confirmation creates a NEW `.txt` draft; the original source byte array and SHA-256 fingerprint remain unchanged. The new file name is bounded and includes a short fingerprint of the new contents. An encrypted private review note records the **complete original source SHA-256** and the count of replaced strings, so humans can reconcile the derivative against its source. This is a **self-reported local provenance hint, not a trusted signature**.
4. The derivative is initially **NOT SELECTED** for outgoing handoffs, marked **Needs human clarification**, and both source and derivative are automatically chosen in the existing local textual comparison UI. Inspect the entire derivative (not just a count) and approve sending it *outside* this app using authentic client/operator identity, consent, scope, revocation and institutional release rules.

**Limits:** Pattern matching is deliberately heuristic and incomplete. An unknown secret, embedded credential, ambiguous multiline key, binary file, encrypted blob, unusual quoting/encoding or private business detail may remain. Replacements can invalidate structured JSON/CSV/ICS syntax: the result is intentionally a UTF-8 text review copy, not a validated replacement for an original Studio scope plan or request. Do not edit a user-signed original or claim cryptographic signing, permission or proof that a document contains no secrets. The human must validate scope and recipient independently. Do not bypass a blocked client packet by changing a self-reported file role or route.

## Studio v1 proposal inspection / human preparation workboard

The standalone vault includes an independent, **read-only** adapter for exact `kind: "lightup.scope_proposal_draft"` / `schema_version: 1` JSON produced by the [Scope Planning Studio v1 owner PR #1567](https://github.com/Zennay/Lightup/pull/1567). No Studio source files or production authorization paths were changed. The embedded scope fingerprint is **not** independently authenticated; this offline adapter binds work to the *actual imported file bytes* via its own local SHA-256 digest.

With a locally imported Studio v1 JSON file, click **Inspect draft locally**. The bounded parser rejects duplicate JSON object keys (including escaped aliases), forbidden prototype keys, malformed/unexpected schema fields, nonliteral authority flags, ambiguous types, excessive array sizes and unsupported UTC interval shapes. It only reads the self-reported text, risk 1–4, `analysis_only` or `authorized_assessment`, declared exclusions, activities and proposed UTC status. It does **not** DNS-resolve, evaluate CIDR membership, validate ownership, recompute the Studio owner's unsigned semantic fingerprint, authenticate a client, inspect network tools or issue permits.

The workboard shows concrete **human follow-up questions** for missing proposed targets/exclusions, risk-4 escalation, private-lab activities, mismatched analysis-only mode, lack of safety instructions, absence of UTC scheduling evidence, and always-necessary client/operator identity, action-time revocation, mandatory CI/security and HUMAN-GO requirements. This is preparation guidance, not an authority decision. The exact raw asset labels remain tucked behind a deliberate private-tab disclosure and are **never copied into the anonymous report**.

The **Add missing decisions to private review note** action appends only source-bound generic question codes to the selected document's private encrypted memo, marks it `Needs human clarification`, and requires explicit user confirmation. It does not submit, authorize, approve, change the original Studio JSON or contact a target. Human work disappears if the tab is locked without exporting a full private archive.

**Review all local Studio v1 proposals** collects a bounded overview of up to twelve imported local JSON candidates. Unsupported or malformed non-Studio files are explicitly counted as excluded, never silently treated as verified drafts. The workboard groups recurring human clarification codes, risk-4 escalation counts and unresolved proposed UTC windows, and displays source SHA prefixes instead of raw target names. Portfolio mode neither changes file statuses nor exports raw assets, identifies a verified client, reconciles tenant authority, checks live grants or issues permissions. Inspect a single original file to update encrypted case notes or export the separate anonymous source-bound checklist.

**Export anonymous portfolio handoff** is available only after the user inspects all currently loaded Studio v1 drafts as a portfolio. It exports a bounded `lightup.offline.studio_scope_portfolio_human_preparation.v1` JSON handoff with the original local SHA-256 source identities, risk/mode, counts of proposed/excluded assets, proposed UTC status, generic follow-up codes, and an explicit count of rejected or incompatible JSON inputs. It also carries seven literal false authority/consent/grant/dispatch/scan/release flags. No filenames, proposed targets, notes, client labels, contact details or casework memos are exported. A changed imported-file inventory since the overview causes HOLD until a new local overview is computed. A document SHA is a privacy-sensitive correlation hint and must only be shared with an appropriate human reviewer; it is neither an authenticated signature nor a scope permit.

**Export anonymous review checklist** creates a bounded `lightup.offline.studio_scope_human_preparation.v1` JSON record with the exact local file SHA-256, requested numeric risk and mode, proposed/excluded counts, UTC status and human follow-up codes. The record includes hard-false authorization, client consent, operator consent, grant, dispatch, scan and release flags. It excludes names, addresses, filenames, contacts, client labels, free-text notes and internal memos. SHA-256 is a **source identity hint**, not a signature, authorization or proof the source was approved. Source-owner status, external real consent and original release gates remain unchanged.


## File format

Outer JSON exposes only the cryptographic parameters and encrypted bytes: exact version, PBKDF2-SHA256, 600,000 iterations, 16-byte random salt, AES-256-GCM, 12-byte random IV, and ciphertext including an authenticated 128-bit tag. Each export uses fresh cryptographic randomness. The AES-GCM additional authenticated data is the constant `LIGHTUP-SCOPE-PACKET-V1`. **Filenames, file count, timestamps, content, self-labelled review roles and per-file SHA-256 digests are encrypted.**

The authenticated inner payload has a version, UTC time, an optional encrypted, self-reported recipient route, an explicit set of literally false action/consent/release flags, and a bounded collection of UTF-8 files with original name, byte size, SHA-256 and encoded bytes. The SHA-256 values are integrity fingerprints, **not signatures, client identity or evidence that consent was granted**. Restoration is atomic with respect to application-level state.

The format is intentionally **not interoperable with actual LightUp execution grants, live tokens, authorization DB records, web request endpoints or scope evaluator claims**.

## Boundaries and caveats

- Untrusted input is only interpreted as a bounded local file or encrypted packet; no HTML preview, script execution, network access, localStorage or server sync.
- Human reviewers must independently authenticate both the actual client and operator, verify exact asset scope and risk, check the current revocation state at action time, and complete the original mandatory CI/security/privacy/release gates. Encrypted export and restore are never approval.
- Avoid importing credentials or customer production secrets. A weak or reused passphrase can be guessed offline; PBKDF2 is a slowing mechanism, not a substitute for a strong passphrase. There is no account recovery or rotation feature.
- In-memory wiping is best-effort; ordinary JavaScript strings, browser downloads, snapshots, caches and OS swap cannot be provably zeroized. A downloaded plaintext file is outside this app's control. Exporting a new encrypted copy likewise cannot revoke previously shared copies. This is a convenience confidentiality tool, **not a regulated secrets vault**.
- Do **not** merge or deploy this isolated new-path feature without the repository's original exact-head hosted and permanently registered VPS CI, independent security/privacy review, source-owner integration and explicit human GO. No tests/QA suites were added or run under the 17 October execution policy.
