# Scope authorization: minimum-safe audit event contract (M7/ST5)

Status: offline acceptance contract only; not an implementation claim.

## Ownership and intent

Production ownership stays with the ongoing execution policy, grant and ToolExecutor PRs. This independent add-only document defines a **deny-safe** audit boundary for future integration. It does not authorize, execute, scan, resolve DNS, interact with targets or change any production module.

An authorization audit event is a *result* of the policy / live-grant decision; it must never become an input that establishes permission. Logging failure must never turn a denial into an allowance, and an audit sink must never invoke a tool handler.

## Allowlisted fields

Only the following scalar fields may leave the execution boundary in a standard audit record:

| Field | Contract |
| --- | --- |
| schema_version | integer exactly 1 |
| event_kind | literal `scope_authorization_decision` |
| decision | literal `allow` or `deny` |
| reason_code | a bounded enumerated, non-secret constant; never the raw exception or `PolicyDecision.reason` |
| interaction | one canonical InteractionKind value |
| timestamp_utc | RFC3339 UTC generated by trusted server clock |
| correlation_id | freshly allocated opaque random identifier, not supplied as authorization evidence |

No raw asset URL, host, IP, query, capability arguments, bearer token, cookie, authorization header, secret, customer-entered note, evidence body, exception message, serialized grant, arbitrary metadata or untrusted free text belongs in the standard record. Do not add grant/client/engagement IDs without a separately reviewed retention and tenant-isolation design.

## Acceptance gates for future source owner

1. Deny without grant, expired grant, revoked grant, closed engagement, asset mismatch, capability mismatch, excessive risk and resolver failure each emit a bounded deny reason or fail safely without an event; zero handler calls.
2. Allow events are emitted only after live revalidation and immediately prior to dispatch; they cannot imply a completed execution.
3. Sink errors cannot bypass policy, leak exceptions or mutate grant/engagement state. Any fail-open authorization behavior fails the gate.
4. Audit event payload rejects additional keys, malformed types and free-text reason injection; no permissive `**kwargs` serialization.
5. Same event schema works with disconnected/no-network tests and documentation-only asset names. Sensitive fixture strings do not appear in serialized output.
6. A concurrent revoke must be resolved by the authorization owner’s linearization gate; this schema cannot substitute for transactional proof.
7. Positive controls show analysis/passive/lab modes do not acquire target-active authority from the logging path.
8. Real SQLite, exact-head Python 3.11/3.14 and permanent self-hosted runner evidence are required before release claims.

The accompanying standalone fixture checker verifies only the shape and redaction constraints of example records. It does **not** prove the executor emits them or that logging is durable. Do not merge this acceptance contract as if it were runtime remediation.
