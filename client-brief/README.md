## Open the working product

**Recommended:** open [standalone.html](./standalone.html) directly; it contains the complete offline app in a single 152,274-byte file, with exact SHA-256 CSP-pinned inline scripts and CSS. SHA-256 of the current bundle: `b1ec34b3a8e3be0f078764c73e2232f1a269b22b69623d1aa31486c566393e9c`. This digest is a packaging fingerprint, **not** a signature or authority receipt. Regenerate locally with `python3 client-brief/package.py`; packaging refuses a changed pinned Casework parser.

**Developer source option:** Open [index.html](./index.html) in a modern browser directly from the `client-brief/` folder, with the sibling `app.js`, `theme.css` and `remediation-engine.js` present. It has no build step, server, external libraries, CDN, runtime network connection, localStorage, persistent database, cookies or service worker. Its top-level CSP is `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'none'`. No target is contacted.

The page consumes only the **original previously authenticated** LightUp findings summary CSV:

```csv
finding_id,title,severity,retest_status,remediation
```

The original source exporter is [`src/lightup/finding_export_cli.py`](../src/lightup/finding_export_cli.py), not this browser interface. For an existing authorised LightUp operator and an authorised engagement, use the **existing** interactive export instructions in [casework PR #1568](https://github.com/Zennay/Lightup/pull/1568). The browser cannot check the exporting identity, consent, tenant or scope. Never use it to collect results from targets.

### Guided offline workspace navigation

After opening original findings, a compact sticky, keyboard-accessible navigator links directly to source, risk dashboard, historical aggregates, scope planning, source-driven actions, human-only discussion board, client handoff and locally resumable drafts. A visible source intake summary identifies which offline input types are actually present; it never shows an authorization readiness percentage, release progress or approval status. The navigator is hidden before a current CSV is opened and when "Forget all imported data" is selected, and it is excluded from print.

### What the product does

1. **Source intake** — select one exported CSV (≤ 1 MiB, ≤ 350 findings). The original `LightUpCasework.parseCSV` refuses unexpected columns, duplicates, invalid severity/retest enums and malformed CSV. A fatal UTF-8 decoder prevents silent character replacement. Optional earlier-source comparison requires an explicit external same-client/**same-engagement** acknowledgement; the CSV itself does not authenticate that assertion. Intake is atomic if either source is invalid.
2. **Executive dashboard** — show total findings, critical/high count, original source-reported regressions and untested count. Accessible severity and source status charts are derived entirely from the uploaded report, not from a new assessment or inference. “fixed” never means verified by this viewer.
3. **Historical review** — compare exact original source fields via the unmodified `LightUpCasework.compareSource` algorithm. Added/changed/absent/unchanged counts are shown without revealing finding IDs by default. **Absent is not resolved** and changed is not improvement or a retest.
4. **Existing Casework link** — optionally import the original Casework v1 planning JSON after a separate same-client/engagement acknowledgement. The imported packet must pass duplicate-key rejection, source-authority false flags, exact current CSV finding-field matching and (when WebCrypto is available) source digest consistency. No raw case IDs, owners, plans, notes or timestamps leave this import; only aggregate self-reported progress stages, overdue count and blocked critical/high count appear in client reports.
5. **Authentic operator-readiness snapshot handoff** — optional original, bounded single-engagement JSON from [operator Authorization Readiness Desk PR #1569](https://github.com/Zennay/Lightup/pull/1569). Export only through its separate actual operator authentication and exact `--client-id` plus `--engagement-id` selection. Import requires separate external same-client/same-engagement acknowledgement and the genuine `lightup.authorization_readiness_operator_v1` envelope with five literal false authority controls. The client briefing independently tallies grant-lineage problems, invalid or unbound approved requests, malformed windows and client-wide pending request flags into an **unsigned, aggregate-only warning area**. The CSV and operator source have **no shared authenticated identity binding**, so the acknowledgement remains an explicit human claim: an apparently clean readiness report is never execution authority. Invalid source, duplicate JSON keys, incomplete grant/request rows or contradictory flag totals, duplicated grant identities, incomplete client-wide request lifecycle and pending requests not matching their original history are rejected without replacing the previous summary. No names, user IDs, grant IDs, request details or notes are included in exported aggregates. **Privacy default:** the attached readiness source can be reviewed locally, but its risk flags are OMITTED from standard client-facing HTML/JSON and from browser printouts. To export them, select **Internal operators only**, separately enable **Include aggregated operator scope-readiness flags**, and explicitly confirm again during HTML, JSON or print output. Switching back to client audience resets the choice. Local source details never establish permission even in internal output.
6. **Human roadmap** — three configurable priority bands with calendar-day follow-up suggestions and an optional ISO date. Values are **illustrative**, never contractual SLAs, booked scans, authorisation windows or evidence that remediation occurred.
7. **Conversation stages** — one local discussion status per priority band (pending, awaiting client, awaiting operator, jointly documented), included in the preview, redacted JSON and private HTML. These are unsigned, self-reported human preparation notes, NOT consent or scope approval. Opening a different source explicitly warns that those stages will be reset.
8. **Client handoff** — generate a self-contained, *script-free* static HTML brief or aggregate-only JSON counters with all ten consent/grant/execution/release flags explicitly false. Default HTML contains no source finding IDs, titles, remediations, hostnames or customer notes. Titles/remediation can be deliberately included for **private authorised recipients only** with an explicit second confirmation and a warning. The private viewer also has a print layout. Human review and secure transfer remain the operator's responsibility.
9. **Resume source-bound human preparation** — Save an independent `lightup.client_brief_working_draft` v1 JSON containing **only** the human brief title, optional date, three planning horizons, self-reported human discussion stages, and original current/earlier source SHA-256 values; all ten authority fields are explicitly false. The original source CSV bytes **must be reopened** before restore. The draft import strictly rejects duplicate keys, unfamiliar fields, altered bytes, malformed dates/roles, missing WebCrypto hashes or false grant/consent flags; no settings are changed on a rejected restore. Even accepted restore resets audience to *Client and operator*, removes sensitive-detail and internal operator-risk sharing, and does **not** bring across casework or operator source files. Saving/download permissions are managed by the browser, so treat the file as private. A SHA-256 is not source authentication or consent.
10. **Scope Planning Studio proposal** — optionally import the original v1 `lightup.scope_proposal_draft` JSON from existing owner [Studio PR #1567](https://github.com/Zennay/Lightup/pull/1567). Requires a separately verified same-client, same-engagement selection, exact original false consent/grant/authorization flags and the pinned Studio canonical CIDR/hostname, SHA-256 revision and local/UTC window parsers. Only bounded proposed asset/exclusion counts, numeric *effective* IPv4/IPv6 address totals, proposed risk/mode/activity labels, UTC planning status and warning count enter the client brief — never raw hostnames/IP ranges, free-text purpose or client labels. All status remains untrusted human planning, NOT authenticated scope or scan permission. The three copied original Studio parser files are byte-identical to source-owner exact commit `71d9e5f760ef2bff46a72b979173bb3181179afb`; the packager checks all original SHA-256 bytes before generating single-file HTML. Reopening a findings CSV clears this proposal and its self-reported cross-document association.
11. **Original Studio proposal revision review** — independently select an earlier Studio v1 source with a separate exact-client/exact-engagement human acknowledgment. Both sources are parsed through the original pinned Studio canonicalizer and effective-scope numeric interval subtraction. The app compares effective IPv4/IPv6 CIDR and exact hostname coverage while excluding declared exclusions, highlights added/removed effective coverage fragments, risk increases, analysis-only→authorized-assessment escalation, newly declared activity types and changed proposed UTC windows. The output is **aggregate-only and review-only**: no raw asset names, identities or addresses are exported. No indication that scope was actually approved, revoked or narrowed at the domain layer. A proposed expansion requires a fresh separately authenticated real approval, not this draft comparison. The earlier source stays in transient memory and is cleared on replacing the current proposal/findings, clearing or forgetting the workspace.
12. **Cross-source human action register** — a single live priority queue combines original critical/high findings, source-reported regressions, disappearing/changing historical findings, self-reported Casework overdue/blocked items, unapproved Studio scope or higher risk, proposal revision expansion and (only when explicitly selected for internal operator use) historical authorization-readiness warnings. Source counts and fixed plain-language recommended *human discussions* appear in the client-facing redacted JSON/HTML, with a downloadable spreadsheet-formula-safe CSV register. The queue never assigns operators, schedules a scan, verifies a retest, changes source records or authenticates permission. An internal-only scope integrity list is never placed in client-facing CSV/HTML/JSON by default.
13. **Human discussion tracker with resumable private progress** — the consolidated follow-up categories now have a separate interactive, source-driven meeting tracker with a human discussion role, self-reported phase and tentative date per category. Roles describe who should be involved, **not real assigned operator/client identities**. Every field remains local in transient browser memory. The private `lightup.human_followup_draft` JSON saves only positional role/phase/date selections, exact current+older CSV source hashes and a digest of the *entire original aggregated action list*. No finding IDs, target assets, client identity, raw grant or operator readiness details leave with the draft; all authority flags remain false. To restore, reimport the same original findings/optional earlier findings, Casework and Studio inputs so the generated action list is exactly the same; otherwise refuse rather than guess the right client or silently reattach stale decisions. Changing the original source inputs or original Studio revision resets local discussion edits. The private saved draft also binds the full source-derived action list, current/earlier CSV SHA-256 and current/earlier Studio revision fingerprints, so it does not transplant an old conversation to changed scope. Client HTML/JSON gets **only counts** of the self-reported discussion stages, not private per-category roles/dates. Saving never schedules an actual event, executes a scan, marks remediation as done or approves a scope.
14. **Client- and operator-safe discussion handoff** — the new meeting tracker provides a filter for urgent categories, unresolved client/operator questions or categories with tentative dates. A separate **private, spreadsheet-formula-safe CSV** export includes category title/count, self-reported human contact role, phase and target date with two literal `FALSE` flags for verified completion/permission. A separate **TENTATIVE all-day .ics calendar** exports only the explicitly dated human discussion categories. Calendar events have unpredictable source-independent random identifiers (never prefixes of source hashes), `STATUS:TENTATIVE`, `CLASS:PRIVATE` and `TRANSP:TRANSPARENT`, and each event explicitly says it is **not an authorized scan window**. Because importing an .ics file into a cloud-synced calendar may share private category labels with its provider, a new explicit disclosure confirmation is required. No background calendar access, accounts or invitations are used. Both files are downloaded only on deliberate user clicks, never on import.
15. **Aggregate briefing history without past raw findings** — import **one to six prior original `lightup.client_security_brief_review` JSON exports** as an ordered set alongside the current authenticated-export findings CSV. Every prior JSON must use the original bounded aggregate schema, literal false authority and SHA-256 current-source fingerprint, strict duplicate-key-free UTF-8, consistency between all severity/status totals and file size ≤256 KiB. Reused/double-counted revisions and conflicting/incomplete source counts reject the entire batch; a failed import leaves the previous review intact. The user separately acknowledges same client and engagement for **every** historic snapshot. File selection order, unsigned source SHA-256 and claims of sameness are *not* authenticated chronology, tenancy, consent, or scope permission. The page includes accessible, offline native progress-bar charts alongside the table for up to seven *reviewer-ordered* points including the current briefing, reported critical/high changes, source regression/fixed counts, proposed scope-risk changes and unsigned Studio revision differences. **Only fully aggregate numeric counts** enter client-facing HTML/JSON; earlier source hashes are withheld. A spreadsheet-formula-safe CSV trend handoff is provided. A source-reported fixed state, declining number of critical findings or a different proposed scope fingerprint never proves a repaired asset, a retest or actual authorization. The integrated human follow-up register adds concrete manual discussions for growth in reported urgent/regression counts, proposed risk/revision differences **or a previously attached scope proposal now missing** (which never proves revocation). The rendered in-browser print preview includes the same aggregate-only historical table and chart as the script-free HTML handoff. Changing or forgetting the primary CSV clears all imported history.
16. **Forget** — clears all source data and DOM rows held by this tab. **Downloaded files remain on disk** and must be deleted separately. No automatic persistence or hidden upload is performed.

### Security / release posture

All source content is untrusted unless independently authenticated using the original service. The CSV source can contain client finding descriptions and identifiers even though the raw export omits target addresses and evidence; therefore work locally, do not post these CSVs or detailed briefs in issue comments and never treat a portable HTML or SHA-256 as signed evidence. A browser may not provide `crypto.subtle` for some file contexts: the UI then marks hashes unavailable rather than faking them. The redacted aggregate JSON intentionally includes source digests when available, which can be correlatable; check before forwarding.

The original mandatory exact-head hosted and permanently registered named-VPS CI, independent security/privacy review, real dual-party authenticated and revocable-at-use consent, #177/#182/#829 source-owner integration and explicit **HUMAN GO** remain unmet. **Do not merge to main, deploy, scan, dispatch, create grants or infer release permission from this separate draft.** This PR is a preview-only deliverable; nothing expands runtime authority.
