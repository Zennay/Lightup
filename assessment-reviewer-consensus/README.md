## Why this exists

The existing workroom handles an operator's choices and pairwise HUMAN plan history. When **2–8 distinct reviewer-exported original PRIVATE HUMAN matrix plans** are available for precisely the same original source files, a coordinator needs to reconcile them without silently discarding diverging stage, route or question choices. This CLI creates a private source-bound proposal that is **directly importable in the original workroom** only if all differences are either uncontested or explicitly resolved. A proposal is never a vote-based authorization or evidence of distinct authenticated people.

## Operator workflow

1. Open the **original 2–8 PRIVATE completed lab-result files** in the existing offline workroom. Each person locally downloads their **plaintext PRIVATE HUMAN plan JSON** from that original workroom. This version accepts original plaintext v1 plans, *not* encrypted-plan/workspace envelopes. If using encrypted exports, independently reopen them in the original workroom and export plaintext inside an approved private environment. Never share original customer data to an unapproved machine.
2. Keep every plan on trusted local storage with `chmod 600 plan-a.json plan-b.json` (and the other selected plans). Every input must be a normal, non-symlink owner-private file. No external targets, DNS, providers or models are contacted.
3. Run `python3 assessment-reviewer-consensus/consensus.py --output /private/new-review plan-a.json plan-b.json`. Select 2–8 **distinct** plans. The output path must **not exist**. All inputs are parsed and admitted before directory creation. Script exits **2** for REVIEW_ONLY proposal or **3** for HOLD/conflicts/errors; never exit 0 as authorization.
4. If there is no conflict, `private-merged-original-plan.json` is emitted. In the existing original workroom, reload exactly the same original result-byte files in the same order and use the original **Resume PRIVATE HUMAN plan** flow for this proposal; all original admission and explicit human confirmation still apply. *Unreviewed/default HUMAN fields remain neutral; a non-default value supplied by one reviewer is a suggestion, not unanimity.*
5. **New standalone PRIVATE browser resolver:** open the emitted `private-resolver.html` file locally, then load the matching `private-resolutions.json` (up to 512 conflicts). Select each field from its **original reviewer-submitted choices** in the accessible table, confirm local download of `private-completed-human-resolutions.json`, protect that downloaded file with `chmod 600`, then re-run the unchanged original plans with `--resolutions` and a fresh output path. CSP has SHA-256 pins for the one inline script and stylesheet and blocks HTTP/remote assets; it never stores originals or reviews in browser storage. The browser is only a convenient editor: **the Python CLI is the final strict source-bound admission**. For larger sets, edit the JSON text directly.
6. **Fast foreground resolution:** instead of editing JSON manually, rerun the original command with `--interactive --output /private/another-new-review`. For up to 512 conflicting HUMAN fields, choose a numbered value drawn **only from original reviewer submissions**, then type `PROPOSE` to confirm the PRIVATE draft. All choices are applied together after the entire original input batch is admitted; on cancellation or invalid selection nothing is published. The resulting `private-resolutions.json` also preserves every actual selected value. For larger conflict sets use the manual packet route below.
7. If conflicts exist, open `private-conflicts.html` locally. Review original source files only in the original source workroom if necessary. Open `private-resolutions.json` in a local trusted text editor and replace **only** each conflict's null `value` with exactly one of its listed original `choices`. The packet contains source fingerprints and original input-file fingerprints, never evidence or target literals. Save it as a new PRIVATE 0600 file.
8. Re-run the same original plan list in the same order with `--resolutions /private/completed-resolutions.json --output /private/another-new-review`. If any original bytes change, if a conflict is missing/altered, or if any resolution is not one of the original choices, **entire batch HOLDS**. The new original-format merged HUMAN plan is published only when all conflicts are resolved.

**Outputs:** `anonymous-counts.json` (counts only, potentially sensitive for small cohorts), `private-resolutions.json` (source/reviewer SHA fingerprints, original choices), `private-conflicts.html` (scriptless local conflict explanation), `private-resolver.html` (offline CSP-bound local browser editor), and **only when fully resolved** `private-merged-original-plan.json` (strict original v1 plaintext format; original app remains final admission authority).

For an interactive proposal, the CLI must have an actual foreground terminal, not a background job or unattended pipeline. Default behavior remains HOLD on unresolved conflicts, never an assumed choice.\n\nEvery output is written to a newly-created **0700** directory, individual files **0600**, exclusive no-overwrite, with filesystem flush. Failures during publication remove incomplete local output. No browser storage, remote calls, service, database changes, new grants, scans, source mutations, workflow files or QA tests.

## Reconciliation semantics

The three original HUMAN enum fields are treated separately by exact **original ordered row ordinal**, not by a reinterpreted title: stage, proposed routing group, next-human-question. Defaults (`needs_review`, `unassigned`, `none`) are absence of a proposal, **not agreement**. For each field, zero distinct non-default submissions means default; one distinct value means uncontested proposal; multiple distinct values trigger HOLD. All 2–8 original `source_sha256` byte-digest lists must be identical and in the same order, with matching 1–16384 original row count. Sparse row ordinals are strictly increasing, all original literal-false authority flags remain false, all original enums are exact, and every input JSON object rejects duplicate keys. Plans are bounded to 3 MiB each, and identical reviewer packet bytes are rejected rather than counted as independent submissions. These checks **do not establish authentic reviewer identities**.

No acceptance of a finding, real vulnerability, remediation, risk reduction, scan coverage, permission, or source authenticity is inferred. Identical source-byte SHA256 values are not signatures. No arbitrary concurrent 'last writer wins'. A subsequent edited plan must still be manually admitted against original sources by the original application. Exports can be highly private and are not automatically safe to share.
