# Scope Schedule Board — offline proposal scheduling

**State:** INCUBATE M3/M7 · PLAN/LAB ONLY · DRAFT/HOLD. This is a human planning tool, not an authorization, consent, approval, booking, grant, evidence of ownership, security scan, permit, or execution path.

## What is delivered

Open **studio/scope-schedule-board.html** in a modern browser alongside **studio/scope-schedule-board.js**. Both files are self-contained, do not need a web server or credentials, make no network requests, and do not read/write the real LightUp SQLite domain database.

Import up to 20 actual lightup.scope_proposal_draft **v1 JSON files** produced by the independent Scope Planning Studio (draft PR #1567). Each file must be at most 64 KiB. The board does not depend on or modify the original Studio's HTML/JS owner paths; it can be used as an offline companion to the Studio drafts.

The board provides:

- **Privacy-limited per-lane tentative calendar export**: choose all draft lanes or only lane 1, 2, 3 or 4 before exporting a transparent TENTATIVE iCalendar file. In single-lane mode, events from other lanes are omitted altogether; only that lane's original/what-if UTC intervals, anonymous ordinal event labels and review disclaimers appear. Export is independently enabled only when the chosen scope is free of overlap, unavailable-block, sub-30-minute-turnaround and optional UTC-workday violations. This is for sharing a proposed schedule with a limited audience; it is not an authenticated roster, booking or assessment authorization.
- **Pin important local proposal times**: each resolved imported source now has a **Pin proposed time in batch rearrangement** checkbox. When pinned, a time already chosen by a human is reserved within its anonymous lane before any unpinned proposal moves; overlaps with other pins, global unavailable periods, less-than-30-minute gaps or selected UTC workday boundaries make the entire batch arrangement fail atomically. Nothing is silently moved around a blocked pin. Pin choices are only local preferences, not client reservations or grants. They round-trip in anonymous review-only scenario JSON and appear in the printable operator brief; older handoffs without a pin field remain compatible. Reverting one/all what-if shifts returns its pinned source to its original proposed time.
- **Four anonymous parallel planning lanes**: assign each imported proposal to a local lane 1–4 in the source inventory. Time collisions, individual first-gap suggestions and batch first-fit scheduling only constrain simultaneous proposals **within the same lane**, while global UTC unavailable blocks and optional daily work hours constrain every lane. Distinct lanes may have overlapping proposed UTC times. These are labels for planning only; no actual operator/team, shift availability, target ownership or security permission is verified. The local review lane is included in unsigned scenario JSON, per-source scenario restores, printable private operator briefs, and anonymous tentative iCalendar event descriptions. Existing v1 scenario files without lanes restore to lane 1.
- **Editable import inventory**: individual imported Studio proposals now appear in a local source list, with their ordinal, risk/mode, UTC-readiness and abbreviated exact-file digest. Each proposal can be placed in one of four anonymous planning lanes or have its current tentative time locally pinned for batch re-planning. One click focuses the UTC timeline on the selected proposal. Removing a single proposal requires human confirmation and immediately removes only its local what-if shift; the original JSON is untouched. Any previously exported ordinal-bound scenario must be regenerated or re-imported with matching order before restore.
- A seven-, fourteen- or thirty-day UTC Gantt-style timeline with proposed interval bars, risk level and view-window clipping.
- A count and readable list of overlaps between supplied **resolved, self-consistent UTC windows**. This is **time-only** comparison, not proof that assets, resources, tenants or people coincide.
- **Optional UTC workdays/hours**: select permitted weekdays and a same-day UTC start/end clock range. With the option disabled (default), schedule placement is unrestricted by a workday. With the option enabled, suggested and batch-rescheduled proposals fit entirely inside the daily UTC window. Current proposals outside it produce clear warnings; tentative calendar export is HOLD until fixed. Workday policy is included in local anonymous scenario exports and restored atomically, never used as a security grant.
- **Review before calendar import**: selecting a private UTC .ics now stages only an in-memory preview of the expanded UTC intervals and the selected target lane; it **does not modify the planning board**. A separate **Add previewed busy times** action atomically inserts only new unique intervals if the total stays ≤30; a **Discard** button clears the preview without side effects. Users can switch between all-lane and per-lane scope while previewing; the visible preview and duplicate/limit calculation update immediately. Metadata remains discarded from the moment the local parser runs. Invalid re-import clears any earlier stale preview instead of mistakenly applying it. This local confirmation does not authenticate a calendar, owner, booking or target.
- **Local recurring .ics busy import**: choose an existing private iCalendar file (≤128 KiB) containing ≤30 VEVENT masters and ≤30 resulting unavailable intervals. Supported are one-off UTC events and **finite UTC DAILY or WEEKLY RRULEs**, with bounded `COUNT` (1–30) or UTC `UNTIL` (at most one year), optional `INTERVAL` (1–12), WEEKLY `BYDAY`, and optional minute-accurate UTC `EXDATE` exclusions (up to 30). Each occurrence must have explicit, minute-accurate UTC DTSTART/DTEND and ≤31-day duration. Every occurrence is expanded locally and discarded if cancelled, transparent or listed in EXDATE. The importer rejects malformed, excessive, unbounded, timezone-local/TZID, RDATE, override/RECURRENCE-ID, invalid BYDAY or nested calendars **atomically**, keeping existing blocks unchanged. Source file names, event labels, attendee emails, organizer, notes and URLs are never retained. No provider login, network or booking verification.
- **Global versus lane-specific UTC unavailability:** choose **All lanes** (default) or only one anonymous planning lane 1–4 when entering a manual blocked interval or importing the events from an .ics. Existing blocks can change their lane association using a dropdown; duplicates within the same lane are refused. A global block constrains all lanes, while a lane-only block affects conflict markers, 30-minute turnaround warnings, first-gap suggestions, pinned-times preservation, collective first-fit scheduling, baseline clash metrics and anonymous calendar exports **only for that lane**. Stored private scenario JSON and printable operator reviews now preserve a small numeric `lane` per unavailable interval; older exports without lane still restore as global. All blocks are temporary local hypotheses, not verified staffing or real calendar authority, and never appear in outgoing .ics. At most 30 unavailable intervals, ≤31 days each.
- Explicit **HOLD** notices for missing, incomplete, ambiguous or non-resolved schedule evidence. Such drafts never produce an event, clash-free assurance, or alternative-time suggestion.
- For every valid proposed interval, a **first possible equal-duration UTC time gap with a 30-minute buffer** relative to the other imported proposals **and the unavailable UTC periods**. No live calendars, owner approval or resource availability is consulted; proposed alternatives are not written back into source files.
- **Before/after impact:** the board shows the original imported proposal clashes alongside the current what-if clashes and net change. A negative improvement means the proposal made the schedule worse; removing time clashes is not actual resource availability.
- **Interactive what-if scheduling**: choose a resolved imported draft, enter a different UTC start time while keeping its original duration, use its first suggested gap, revert one shift or revert all shifts. Each local edit immediately updates the timeline, warnings, alternate slots and calendar export; the original Studio JSON and stored request are never changed.
- **Bounded multi-draft arrangement**: first-fit reschedules all resolved draft intervals around each other and local unavailable blocks, with a minimum 30-minute buffer within each anonymous lane. Any proposal requiring more than 31 days of shift **relative to its original imported UTC start** fails the entire operation atomically, preserving the earlier what-if scenario. This bound holds even when starting from a previously shifted what-if interval. A clash-free speculative proposal never means resources or targets are authorized or free.
- **Original-file content continuity**: on proposal import, the browser computes a SHA-256 over the **exact original JSON file bytes** (when Web Crypto is available). Every scenario row carries that source-file digest; restoration requires the same original bytes and original interval/mode/risk at the matching ordinal. This reduces accidental cross-proposal substitution but **does not authenticate the client, the file's author, scope ownership or consent**. Without Web Crypto, normal calendar planning is still possible, but source-bound scenario JSON export/restoration is held (not silently weakened).
- **Return changed planning times to Studio**: select a resolved, explicitly shifted draft and reselect its **exact same original JSON bytes**. The board verifies SHA-256 content continuity and computes new timezone-local start/end and offset evidence from the source's original IANA timezone using `Intl.DateTimeFormat`. DST-repeated local hours, unsupported zones, mismatched original bytes, non-31-day-bounded shifts and malformed source files are HOLD. A new regular Studio v1 JSON file is downloaded with the original target/notes/mode/risk context and changed time fields. The old scope fingerprint is intentionally removed (no stale revision digest carried forward); all grant/consent/execution booleans remain false, and the original source is never modified. **This exported revision contains sensitive scope targets and notes**, unlike the anonymous scheduling review files. It must be independently re-reviewed and, where relevant, submitted through the existing authenticated client/operator workflow. No automatic submission, authorization, scan or database mutation.
- **Interactive conflict cards**: apply the first valid alternative directly from the proposal's scheduling card without finding its record in a separate form. Source files remain untouched until an explicit, verified revised-draft download.
- **30-minute buffer awareness**: visual notices and a separate counter identify back-to-back draft events in the same lane, or draft-to-unavailability gaps shorter than 30 minutes, even when the windows don't overlap. Tentative transparent calendar export is held while any overlap, local unavailability, buffer-gap or enabled-work-hour breach remains. The print-ready private review brief and unsigned scenario JSON remain available to discuss unresolved issues. New JSON handoffs record their buffer-violation count, which must match the restored proposed windows. Older pre-buffer-count handoffs remain readable.
- **Scenario restoration**: reload a previously exported review-only scenario only after loading the same number/order of original Studio proposals with exactly matching source file SHA-256, UTC start/end and requested risk/mode. Shifted intervals must preserve duration and remain within 31 days of their original; local unavailable blocks are restored atomically. If *any* field is malformed or incompatible, the entire import is HOLD without modifying the active scenario. This is a convenience consistency check, **not cryptographic source identity verification**, and assets/names are intentionally not present in the handoff.
- **Privacy-minimal printable operator review brief**: a standalone HTML export now summarizes the current original versus proposed UTC windows, anonymous ordinal labels, source-file SHA-256 continuity hints, requested risk/mode, current workday rules, blocked UTC periods and unresolved scheduling concerns. The document uses escaped text, no embedded scripts, no external assets, and a restrictive content-security policy. It is untrusted, can be stale, and can reveal proposed timestamps to whoever holds the downloaded file. It has no target hostnames, client identities, contact details, raw notes, grants, credentials, links, source file bodies or scan capability. Never treat it as approval, permission or a booking.
- **Unsigned scenario JSON handoff**: export per-tab ordinal source and proposed UTC intervals, shifted flags, local unavailable windows and overlap counters. Omits client identifiers, actual targets, names, contacts, notes and raw source proposal contents; the file still exposes sensitive scheduling times and is **not portable proof of identity or consent**. Ordinals only refer to the current tab's import order. No scenario is submitted automatically.
- Print-friendly review view and an **anonymized .ics** export. Every exported event is STATUS:TENTATIVE, TRANSP:TRANSPARENT, with synthetic per-export UID and no invitation recipient, attendee or organizer. No assets, tenant labels, personal notes, client name, contacts or source IDs enter the calendar file. It *does* contain the proposed UTC times, which should still be treated as sensitive when shared.

## Usage

1. Obtain v1 JSON exports from Scope Planning Studio. Save them locally on a trusted device.
2. Open studio/scope-schedule-board.html locally, choose up to 20 files. Inspect the imported-proposal inventory to focus an individual proposal or remove an obsolete local import without clearing the others.
3. Select a UTC start day and 7/14/30-day horizon. Optionally configure UTC workday boundaries, add manual blocked intervals or import finite daily/weekly UTC .ics busy windows. Choose global or lane-only scope for each imported calendar or manual block; review an imported calendar's time-only preview before explicitly applying it, or discard that preview. The existing block list permits later reassignment. Only UTC times and the lane number are retained. Read the overlapping-window, unavailability and missing/unsafe-window HOLD notices.
4. Optionally assign proposals to separate anonymous planning lanes, then apply a local what-if time shift. Pin any important tentative times before using the batch re-planner. Apply feasible suggestions directly in their cards. To create a revised Studio v1 draft carrying the selected new time, reselect the exact original file and download its explicitly non-authorizing draft revision or generate a bounded first-fit scenario for all resolved drafts. Export a private printable operator brief (HTML) or original-preserving scenario JSON. Do not distribute these sensitive times outside an authenticated channel. For a previous scenario, first import its original Studio drafts in the same order and then restore the local review-only scenario JSON. View the resulting proposed overlaps and export an anonymous scenario JSON for private review. Use the slot suggestions only as conversation starters during independent client/operator review. Export the anonymous **tentative** calendar if needed.
5. For limited sharing, select one planning lane in the anonymous tentative calendar export picker; other lanes' proposed times are excluded. For any real proposed scheduling change, edit and re-export the **original Studio draft** and repeat authenticated intake/consent. The schedule board deliberately never changes or approves an existing proposal.

## Import and integrity

The import checks the original v1 schema shape, explicit **false** authority flags (including revocation_checked), requested-mode/risk types and bounds, bounded asset arrays and metadata, a bounded UTF-8 file, real local date components, exact UTC instants of the form YYYY-MM-DDTHH:MM:00.000Z, offset values and exact wall-time/UTC offset consistency. The claimed IANA timezone name is **not authenticated**. A supplied scope_fingerprint_sha256 is validated only for syntax: this board does **not** independently validate that Studio's original canonical fingerprint or any signature corresponds to trusted identities. Import is always considered untrusted and informational. Any corrupted or unknown source structure is rejected or excluded from calendar computations, not repaired.

The board does not parse scope semantics or contact assets and therefore deliberately **cannot** tell whether two clients own the same IP, whether a public endpoint is authorized, whether a CIDR exclusion actually protects a target, whether an operator approved the risk or whether a revocation happened after the draft. It never uses a saved local client/operator session, accesses the network, issues a scan, or calls an execution handler. The DRAFT_ONLY status cannot be promoted through this interface.
