# LightUp Authorization Risk Portfolio

**INCUBATE M3/M7 · PLAN/LAB ONLY · DRAFT/HOLD · REVIEW_ONLY.** This is an isolated, offline human operator product, not a second authorization system.

## What is delivered

- Load **1–12 real previously generated private JSON exports** from the separately owned [Authorization Readiness Desk, PR #1569](https://github.com/Zennay/Lightup/pull/1569). Exports are genuinely operator-authenticated **at original creation time**, but copies brought here are **unsigned, untrusted, potentially stale**. The interface does not reauthenticate either a user or a tenant.
- Atomic bounded imports, duplicate JSON key denial, exact schema and canonical original grant-window labels (no invented authorization statuses), literal five-false authority envelope, exact selection scope duplication rejection, report/record identity and count consistency checks. A failed import preserves the last accepted workspace.
- A **multi-scope risk board** with critical/high/other recorded warnings, pending genuine client-request counts and stored grant records (which never imply permission), filtering and separate *self-reported* human escalation/discussion stages.
- **Cross-scope source-revision reconciliation:** pseudonymous source exporter record keys are compared only in memory during atomic admission, then discarded. The UI reports counts of overlapping stored records, unchanged revisions and different source revisions across original selections; a disagreement prompts original-source human review, not automatic permission or a claim of verified chronology. A separate cross-scope theme table groups original flag categories by affected report count and occurrence.
- **Historical multi-revision source lens:** load 2–8 original strictly parsed operator JSON snapshots of the **same exact selected scope** (each capped), inspect original pseudonymous row identities only transiently to count NEW/CHANGED/ABSENT/UNCHANGED adjacent stored revisions, and compare all original fixed warning-category counts across reviewer-selected files. Display order is **NOT verified chronology**. Download a completely anonymized aggregate history CSV; the app does not retain or export original source hashes, record keys, host/IP, clients, notes or filenames. This is independent of PR #1569's original single-pair comparison, and does not change its owned files.
- **Per-original-warning category casework:** source-scope-specific review table of fixed original exporter flags, their severity and source-reported counts, self-reported triage state and fixed coordinating team. Fixed safe source-warning-specific human reviewer questions help route genuine request/tenant/scope evidence to the right source owners. Bounded (180-character) free-text personal discussion notes are **private resume only**; aggregate CSV and JSON intentionally exclude them, even though those files include fixed teams and statuses. Aggregate manual CSV and JSON handoffs and **private original-byte-bound status restore** preserve per-flag stages. There is no automatic issue creation, request decision, client communication, verified repair, grant or scan. Earlier private drafts can load with default category states; revised original source files invalidate all saved local states.
- **Optional calendar handoff for human follow-up only:** download a bounded tentative all-day `.ics` file for open review scopes with an independently entered UTC date, using only anonymous numbered source slots, fixed teams and generic review urgency. A separate explicit warning/confirmation is required because importing a calendar file may later sync it to a cloud calendar. The file contains no original assets, client/engagement identities, notes, or credentials and creates **no** actual scheduling, scanning, access, consent or incident revocation.
- **Human follow-up routing and target dates:** each source scope has a self-reported fixed team (unassigned/security/privacy/client-operations/platform) and strictly checked UTC target date; filter tasks whose selected due date passed. The local stage does not issue work orders, meetings, remediations or consent. Routing is carried through aggregate coordination files and source-exact private restore, with backward-compatible defaults for earlier locally saved drafts.
- A cross-scope human review-hours capacity projection using bounded, editable per-severity effort and weekly hours. The eight hypothetical weeks deliberately create **no commitments**, staffing orders or scans.
- **Historical review coverage:** the exporter’s normal summary includes pending requests and stored-grant flags; the portfolio additionally surfaces original **approved/rejected request-history warnings** that are not counted in its open-request queue (not a fabricated approval or new authority).
- Privacy-minimal manual CSV, JSON and Markdown exports for human coordination. They use numbered source slots and fixed flag names; original host/IP, client/engagement labels, filenames, source pseudo-IDs, credentials, original case notes and source digest are absent.
- Downloadable **eight-week human review capacity CSV** with priority-banded hours, unallocated hours and explicit non-authorizing false flags. Hours are hypothetical review labor, not a scan plan, case SLA or capacity attestation.
- Optional **private** resume JSON containing only original-byte SHA-256 fingerprints and local discussion states. Restore requires reimporting **identical original files in identical order**. WebCrypto unavailability disables the resume feature without rejecting otherwise valid sources. Fingerprints are not signatures.
- Restrictive SHA-256-pinned inline CSP and reproducible single-file **`standalone.html`**. No remote scripts, network requests, browser storage, IndexedDB, cookies or targets.

## Operator use

1. In a separately approved local LightUp checkout, use the existing PR #1569 authenticated operator command to create private JSON reports:
   `PYTHONPATH=src python -m lightup.authorization_readiness_cli --db /path/to/private.db --email operator@example.com --client-id EXISTING-CLIENT-ID --output /private/readiness-01.json`.
   The original command prompts for the operator's password (never put one in arguments). Obtain several **distinct** scope selections with review rights; no client identity is inferred from a copied file.
2. Open **`standalone.html`** directly in a modern browser; import original JSON snapshots locally (max 2 MiB each, 8 MiB batch).
3. Inspect source-wise flagged findings and human triage stages, adjust staffing estimates; download only the intended aggregate handoff. If saving a private resume, protect it and the original source exports as sensitive operator documents.
4. Restore later by first importing exactly the original files again in the same order. A different source revision must start with fresh human status rather than silently importing approval or a previous triage result.

For maintainers: run `python3 authorization-portfolio/build.py` to reproduce the bundled file; it uses only the Python standard library. A syntax-only `node --check authorization-portfolio/app.js` can inspect the generated script. **No QA, regression or testsuite is added or required by this feature branch.**

## Source safety and overlap limits

The source's selected scope fingerprint is opaque. Cross-scope overlap can be observed only for matching original record pseudonyms; its absence does **not** prove distinct cases or tenants. Distinct exported scopes **may still overlap** in clients, grants, and requests. The app refuses combining an all-client snapshot with narrower ones, refuses duplicate scope fingerprints, and labels every sum as **possibly double-counted**. Report flags and records are reviewed **as documented by their original exporter**; no ground truth, active revocation, issuance permission, chronological validation, authenticated proof of origin, or tenant ownership can be concluded from a file. A source file with an unexpected schema is **HOLD**, not silently downgraded.

The app does not modify domain, grants, webapp, entrypoint, activation, authorization policy, CI, runners, or independent worker-owned source. It performs no credential handling, real target interaction, permission issuance, incident STOP, grant revocation, dispatch or scan. Original source owner fixes [#177](https://github.com/Zennay/Lightup/issues/177), [#673](https://github.com/Zennay/Lightup/issues/673), [#829](https://github.com/Zennay/Lightup/issues/829) and other source branches remain separate.

**Do not merge, deploy to production, issue grants, or scan based on this product** without original exact-head hosted CI, permanent registered VPS CI, independently authenticated client/operator consent and action-time revocation, security/privacy review and explicit HUMAN GO. Human stages marked 'discussed' are always **unverified**.
